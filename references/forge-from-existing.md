# 场景 C：改造他人作品（forge-from-existing）

> 把别人的 Skill/MCP 改造成自己的。最高风险场景——法律红线与安全红线在前，改写在后。

## 第一道闸：许可证审查（不过此闸，禁止改写）

| 许可证 | 能否改造分发 | 条件 |
|---|---|---|
| MIT / Apache-2.0 / BSD | ✅ 可以 | 保留原版权声明与许可证文本 |
| CC BY / CC BY-SA | ✅ 可以（谨慎） | 署名；SA 要求同许可证分发 |
| GPL 系列 | ⚠️ 谨慎 | 传染性：衍生作品必须同许可证开源 |
| **无 LICENSE 文件** | ❌ **不能直接改了发** | 默认保留所有权利。只能：①学思路自己重写（思想不受版权保护，表达受保护）②联系作者要授权 |
| 明确禁止商用/修改 | ❌ 不行 | 尊重作者 |

**实例警示**：归藏的 guizang-material-illustration 仓库就**没有 LICENSE**——学它的思路可以，拿它的文件直接改是侵权。改造归藏作品前逐仓查 LICENSE。

## 第二道闸：安全审计（参考 SlowMist agent-security 分类法）

逐文件扫描以下红线，命中即放弃或重写：
1. **凭据收集**：读取与本功能无关的环境变量、SSH key、浏览器 cookie
2. **数据外发**：向不明域名发送用户数据；base64 混淆的请求
3. **恶意安装器**：`curl xxx | sh`、下载执行远程脚本
4. **隐蔽执行**：混淆代码、与功能无关的定时任务/钩子
5. **过度权限**：声明的权限超出功能所需

## 第三道闸：结构解剖

把原 SKILL.md / MCP 源码逐段标注"这段在解决什么问题"：
- 哪些是**工艺精华**（澄清流程、防御检查、约束设计）→ 保留学习
- 哪些是**作者个人印记**（他的场景、案例、审美、语气）→ 替换成昊哥的
- 哪些是**环境依赖**（特定平台机制、特定 API）→ 按目标平台重写

## 改写四替换

| 替换 | 说明 |
|---|---|
| 场景替换 | 原作者的使用场景 → 昊哥的业务场景（如：设计博主场景 → 汽车后市场获客场景） |
| 语气替换 | 原文的表达习惯 → 昊哥的直接短句风格 |
| 案例替换 | 原案例 → 昊哥领域的真实案例 |
| 依赖替换 | 外部服务/API → 昊哥实际可用的（扣子/得到大脑/GitHub 等） |

## 产物要求

- 保留原作者 provenance 标注（"思路源自 XX，许可证 XX"）——即使许可证允许不署名，熔炉产物也保留来源说明，这是诚实纪律
- 《建造档案.md》记录：原仓库地址、commit 版本、许可证、改了什么、为什么改

## 验收

除标准清单外增加两项专项：
- 许可证合规复查（产物里的声明与动作一致）
- 与原版本的功能对比测试：改造后核心能力不弱于原版（除非有意裁剪）
