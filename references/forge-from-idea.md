# 场景 B：口述想法迭代（forge-from-idea）

> 用户只有一个想法，通过口述澄清逐步建成。最考验澄清功力——想法在用户脑子里，熔炉负责把它问出来、定下来。

## 流程

### Step 1 · 七问澄清访谈（借鉴归藏 7 问法，一次最多问 3 个）

| # | 问题 | 为什么问 |
|---|------|---------|
| 1 | **这个技能给谁用？在什么场景下用？** | 决定定位与语气 |
| 2 | **用户会说什么话触发它？**（原话举例 3 句） | 直接转化为 description 触发词矩阵 |
| 3 | **理想的产出长什么样？**（文件/回复/动作？给个样子） | 决定产物形态 |
| 4 | **什么事它绝对不能做？** | 边界声明，防误触发 |
| 5 | **有没有参考对象？**（见过的类似技能/工具/人工作法） | 锚定预期，少走冤枉路 |
| 6 | **它需要读什么资料/调什么外部服务吗？** | 决定 references 内容和是否要走 MCP |
| 7 | **怎么算做好了？** | 验收标准前置（铁律4） |

用户答不上来的问题，给 2-3 个候选答案让他挑，不逼开放题。

### Step 2 · 大纲落盘确认
产出《技能大纲-v1.md》，包含：定位一句话 / 触发场景 / 工作流程草案 / 产物形态 / 验收标准。**用户确认前不动手写 SKILL.md**——结构定了再翻修代价高。

### Step 3 · 最小可用版（MVS）
先建最小可用版本：SKILL.md + 最关键的 1-2 个 reference。不追求一次完备。
在真实环境跑一次，拿真实反馈。

### Step 4 · 迭代循环
每次迭代：
1. 用户反馈 → 定位问题在哪一层（触发不准？流程不对？产出质量差？）
2. 改对应层：触发问题改 description，流程问题改工作流，质量问题改 references/约束
3. 版本号进位，更新《建造档案.md》

## 迭代排障速查

| 症状 | 病根 | 改法 |
|---|---|---|
| 该触发时不触发 | description 触发词没覆盖用户说法 | 把用户原话加进 description |
| 不该触发时乱触发 | 缺"何时不用"边界 | 补边界声明 |
| 产出每次不一样 | 约束太松 | 收预设选项，减自由度 |
| 产出结构对但内容浅 | references 的专业料不够 | 补 references，不是加长 SKILL.md |
| 某步骤模型总犯错 | 缺防御性检查 | 加显式预检步骤 |

## 纪律
- 用户口述中的**原话金句**直接进产物（触发词、语气示例），不二次加工
- 每轮迭代只改必须改的，不顺手重构没坏的
- 想法类技能早期不求完美，求"真实环境跑起来收反馈"
